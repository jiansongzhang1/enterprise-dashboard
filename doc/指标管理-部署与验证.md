# 系统管理 · 指标管理（口径与取数方式）部署与验证

2026-10-26

## 做了什么

每个指标的**业务口径**和**取数方式**收口到 `dashboard_metric_card` 一张表，管理后台「系统管理 · 指标管理」可以查看和维护。

**不改线上取数**：运营总览、指标汇总（以及判定引擎、回测预览）仍按启动时加载的配置取数，向 UDS 取哪个字段仍以 `application.yml` 的 `dashboard.gateway.uds` 为准，跌幅基准以 `monitor.engine.baseline-fields` 为准。表里新增的字段是这些配置的「登记」，页面「對照」一栏标出表和配置不一致的地方。没有改动任何现有 Java 代码（只新增文件），`MetricRegistry`、`DashboardConfigMapper`、取数网关都没动。

| 内容 | 存在哪里 |
| --- | --- |
| 业务口径与备注 | `remark`，格式「口径：…」+ 换行 +「备注：…」（口径取自《Yata v0.1 操作指南 · 指标口径》与页面 ⓘ 文案） |
| 小时 / 日 / 金额数据集的 UDS 字段 | 新增 `uds_hour_field` / `uds_day_field` / `uds_amount_field`（对应 `dashboard_overview_hour_v2` / `_day_v2` / `_amount_v2`） |
| 跌幅基准列 | 新增 `uds_baseline_field` |
| UDS 上游原始表 / 字段 | `source_table` / `source_field`（旧值是早期直连 Doris 的表名，已清空，待 UDS 提供；备份在 `dashboard_metric_card_bak_20261026`） |
| 后端组装（存提差、NGR、派彩） | 仍在 yml 的 `overview.subtract` / `add`，页面只读显示 |

运营总览 ⓘ 的繁体口径文案仍在代码 `OverviewMetricText` 里，和表里的口径内容一致；以后要让页面直接读表，需要另外改代码。

## 页面规则

- **已接入**（`status = '0'`，现有 28 个）：只能改口径、上游原始表 / 字段、四个 UDS 字段；名称、分组、格式、计算、监控属性只读；不能删除。
- **仅登记**（`status = '1'`，后台新增的都是）：运营总览、指标汇总不加载，不上卡、不进页面、不能建告警规则；还能改名称、分组、格式、方向、更新频率；没有被页面、告警规则、异常事件、其他指标（分子 / 分母 / 最小样本量）引用时可以删除。要真正接入取数，需要另外改 yml、SQL 并发版。
- 修改接口里没传的字段沿用原值，传空串表示清空。

## 接口

| 方法 · 路径 | 用途 | 权限 |
| --- | --- | --- |
| GET /system/metrics?keyword=&groupCode=&status= | 列表：rows（含 config 线上配置、configMismatch、pages、ruleCount、usedBy、deletable）、groups、datasets | system:metric:list |
| GET /system/metrics/{metricCode} | 详情 | system:metric:list |
| POST /system/metrics | 登记新指标 | system:metric:add |
| POST /system/metrics/{metricCode}/update | 修改 | system:metric:edit |
| POST /system/metrics/{metricCode}/delete | 删除仅登记、无引用的指标 | system:metric:remove |

校验失败返回 `code = 400`，`data.fields` 列出每个字段的错误（繁体）。

## 部署步骤

1. 执行 SQL（dashboard_db，都可重复执行）：

   ```bash
   psql -X -v ON_ERROR_STOP=1 -d dashboard_db -f sql/alter_metric_card_dictionary_postgresql.sql
   psql -X -v ON_ERROR_STOP=1 -d dashboard_db -f sql/add_metric_manage_menu_postgresql.sql
   ```

   第一个脚本末尾应输出 `total = 28, with_definition = 28, with_upstream = 0`。重复执行不会覆盖后台已维护的口径和字段。
   新环境：`dashboard_metric_card_postgresql.sql` 已含新列和口径，再执行一次 alter 脚本无变化；`migrate_appdb_to_dashboard_db.sh` 已加入这两个脚本。
2. 发布后端（先执行 SQL 再发后端：列表查询读新列）。
3. 发布 admin-frontend（`./bin/deploy-frontend.sh test`），重新登录后台，「系统管理」下出现「指标管理」。

回滚：alter 脚本末尾有回滚语句（从备份表恢复 remark 和 source 列）；新增的 4 列留空即可，不影响取数。

## 验证

本地已做：

- 后端单元测试 104 项通过（新增 `MetricDictServiceTest` 10 项：对照、引用、筛选、登记、已接入只改口径、仅登记可改基础列、删除限制）。
- PostgreSQL 16：旧建表脚本 + alter 与新建表脚本 + alter 的列、约束、数据完全一致；alter 执行两次结果不变，后台改过的口径不被覆盖。
- MyBatis 实跑 `MetricDictMapper.xml` 全部 11 条语句；用真实 `application.yml` 绑定配置对照，28 个指标全部「一致」。
- 插入一条仅登记的指标后，`MetricRegistry` 启动校验照常通过，加载的指标、指标墙、可选列数量不变（运营总览、指标汇总不受影响）。
- admin-frontend `vite build` 通过。

测试环境：跑 `doc/system-metrics.postman_collection.json`（15 个请求，会登记一个临时指标再删除）；页面上检查 28 个指标的「對照」都是「一致」。
