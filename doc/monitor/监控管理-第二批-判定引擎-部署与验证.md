# 监控管理 · 第二批（判定引擎）部署与验证

设计文档：「监控管理 · 后端设计方案」→ 判定引擎 → 实现设计；接口页「后台任务逻辑细化」。

## 本批内容

| 范围 | 内容 |
| --- | --- |
| 判定引擎 | 每 10 分钟（IST :00 / :10 / … / :50）逐站点处理上一个完整小时：取数 → 判定 → 写事件 / 运行状态 / 待发送记录 |
| 取数 | 每个站点每轮只发 **1 次** UDS 请求，从 `dashboard_overview_hour_v2` 一次取回全部字段（规则指标、派生指标分子分母、样本量指标、跌幅基准）；只有第 1 次失败（非「数据未就绪」）才发第 2 次，**最多 2 次**。不走页面用的水位退避 |
| 落库判断 | 本次响应的水位 `meta.freshness.watermark ≥ H + 1 小时` 视为 H 点已落库；值为空的指标等下一轮，:50 仍为空的指标这一小时不判定（中断连续计数）：**不告警、不写记录、不发通知**（2026-10-22 与产品确认，原来的 `data_missing` 记录已去掉） |
| 判定 | 纯函数 `MonitorJudge`（下限 / 上限 / 区间 / 跌幅、检测周期、连续 N 次、注意升级、样本量、可升可降、恢复），回测预览下一批直接复用 |
| 通知 | 事件严重且未处理时写 `monitor_notify_log`（pending，消息内容已生成）；**发送任务在 Lark 批次实现**，本批不实际发出 |
| 规则上限 | 一个站点一个指标只能有一条规则（唯一索引，已有）；新增：每个站点同时启用的规则最多 40 条（`monitor.max-enabled-rules-per-site`），新建 / 启用超过时返回 4807 |

## 部署步骤

1. **执行增量 SQL**（dashboard_db，可重复执行）：

   ```bash
   psql -X -v ON_ERROR_STOP=1 -d dashboard_db -f sql/alter_monitor_engine_postgresql.sql
   ```

   末尾自检输出 `monitor_engine_columns = 6`（含 2026-10-21 新增的 `monitor_event.stopped_at`：规则暂停 / 删除、事件改为 stopped 的时间，异常事件「持續」列悬停要用）。已经执行过旧版本的环境重新执行一次即可：2026-10-22 版会删除之前写入的 `event_type = data_missing` 记录、去掉 `uk_monitor_event_missing` 索引，并把 `event_type` 约束收紧为只能是 `alert`、`monitor_notify_log.msg_type` 只能是 `alert / test`。新环境直接执行 `monitor_schema_postgresql.sql` 已包含这些列；`migrate_appdb_to_dashboard_db.sh` 的 build-tmp / upgrade / verify 已加入本脚本。

2. **配置**（环境变量，未配置时取默认值）：

   | 变量 | 默认 | 说明 |
   | --- | --- | --- |
   | `MONITOR_ENGINE_ENABLED` | `false` | 判定引擎总开关；关闭时不注册定时任务、不开启 Spring 定时调度 |
   | `MONITOR_MAX_ENABLED_RULES` | `40` | 每个站点同时启用的规则上限 |
   | `MONITOR_ENGINE_POLL_CRON` | `0 0/10 * * * *` | 轮询节奏，时区取 `dashboard.timezone` |
   | `MONITOR_EVENT_PAGE_URL` | 空 | 告警消息里「查看」的地址 |
   | `MONITOR_TEST_CHAT_ID` | 空 | 管理后台「手动触发测试告警」固定发到的 Lark 群（oc_ 开头）；机器人须已在群里；不配时该接口返回 400 |

   跌幅基准列在 `application.yml` 的 `monitor.engine.baseline-fields` 下配置（指标编码 → `dashboard_overview_hour_v2` 的列名），**列名等 UDS 给出后再填**。没配置的跌幅类规则会在规则列表显示「判定失败：跌幅基準字段未配置」，其他规则不受影响。

3. **上线顺序建议**：先部署代码（引擎默认关闭，对现有功能无影响）→ 在测试环境打开 `MONITOR_ENGINE_ENABLED=true` 观察 2～3 个小时 → 确认 UDS 水位按小时推进（待确认 #8）、基准列名（待确认 #7）后再在生产打开。

4. 多实例部署时依赖 Redis 锁 `monitor:lock:poll`（TTL 540 秒）保证同一时刻只有一个实例在判定；Redis 不可用时本轮跳过并记错误日志。

## 验证

### 本地已做的检查

- 判定纯函数 81 项断言（状态机触发 / 升降 / 升级 / 恢复、零星越线、未判定中断、断档、四种判定类型的边界、样本量、回测段与最差值、4 小时周期升级、72 小时回看）全部通过。
- 引擎流程模拟（假数据库 + 假 UDS，27 项断言）：同一小时不重复取数；水位未到时等待、:50 仍缺的指标不判定；含缺失小时的 4 小时周期不判定；第 1 次 UDS 失败第 2 次成功共 2 次请求；两次都失败本轮不处理；规则没有通知群记 unset；基准列未配置写 judge_error；服务停过的小时标 missing。全部通过。
- `MonitorEngineMapper.xml` 全部语句、`MonitorRuleMapper` 新语句在 PostgreSQL 16 上执行通过；新建库与升级库的 monitor_* 表结构一致；`ck_monitor_event_level` / `uk_monitor_event_missing` 的约束行为符合预期。
- `MonitorMapperScopeTest` 通过（新 select 都带站点条件）。

### 测试环境打开引擎后

1. 准备：确保至少有一条启用规则（第一批 Postman 集合可建），`MONITOR_ENGINE_ENABLED=true` 重启。
2. 日志：每 10 分钟一条 `[monitor] 站点 SITE-IN 数据小时 … 落库=true 待处理 n 条，本轮处理 n 条`。
3. 数据库核对：

   ```sql
   -- 每小时一行：judged / missing；waiting 只应出现在当前处理中的小时
   SELECT data_hour, status, check_count, judged_at FROM monitor_hour_check ORDER BY data_hour DESC LIMIT 6;
   -- 每条启用规则的进度：last_data_hour 应等于上一个完整小时
   SELECT r.rule_no, r.metric_code, s.last_data_hour, s.recent_levels, r.last_judged_at, r.judge_error
     FROM monitor_rule r LEFT JOIN monitor_rule_state s ON s.rule_id = r.rule_id
    WHERE r.del_flag = '0' AND r.enabled ORDER BY r.rule_no;
   -- 告警事件（数据缺失不写记录，这里只会有 alert）
   SELECT event_id, rule_id, event_type, level, status, start_hour, trigger_hour, end_hour, notify_status, handle_status
     FROM monitor_event ORDER BY event_id DESC LIMIT 20;
   -- 待发送（Lark 批次上线前会一直是 pending；每个事件最多一条 pending）
   SELECT id, event_id, chat_id, status, left(content, 60) FROM monitor_notify_log ORDER BY id DESC LIMIT 10;
   ```

4. 造一次告警：把某条规则的严重线调到当前值附近（例如存款成功率下限设 99.99%、连续 1 次），下一个整点后应出现一条 `alert` 事件、一条 pending 发送记录，消息内容形如：

   ```
   【uWin】Yata 告警 · 嚴重
   存款成功率：近 1 小時 97.12%，低於嚴重線 99.99%
   起點 09:00 · 已持續 1 小時 · 規則 R-001 · 負責人 zhang@yata.demo
   ```

5. 手动触发测试告警（2026-10-23）：执行 `sql/add_monitor_rule_test_permission_postgresql.sql`（建按钮权限 `monitor:rule:test` 并授给 admin），配置 `MONITOR_TEST_CHAT_ID` 后重启，再重新发布 admin-frontend。管理后台「系統管理 · 通知模板」页「手動觸發規則（測試）」选站点、规则后点「觸發測試告警」：测试群收到一条「【測試】」开头、用最近一个已结束周期真实数据渲染的告警，页面显示周期、当前值 / 基准、判定级别和消息原文；`monitor_event` / `monitor_notify_log` 不新增记录。也可用 Postman 集合第 12 组。

6. 规则上限：测试环境设 `MONITOR_MAX_ENABLED_RULES=1`，已有 1 条启用规则时再新建（enabled=true）或启用另一条，返回 `{"code":4807,"msg":"本站啟用中的規則已達上限 1 條，請先暫停其他規則"}`。

## 已知限制 / 待确认

- 发送任务（Lark）在下一批：本批只写 pending 记录；规则的 `last_notified_at` 由发送成功后更新，所以静默期要到发送任务上线后才生效（同一事件已有 pending 记录时不会重复追加）。
- 运营总览的判定缓存（Redis `monitor:state:{site}`）在总览批次实现，本批只写数据库。
- 区间类规则的样本量口径 `betU` 还没有 UDS 字段：取不到样本量时不做样本量拦截（按有样本判定）。
- 待确认 #7：跌幅基准列名；#8：`dashboard_overview_hour_v2` 的水位是否按站点、按小时及时推进——水位停滞时全站指标在 :50 后都不判定（不告警、不记录）。
- UdsClient 自身对限流（429）的等待重试不计入「最多 2 次」。
- 2026-10-22 起数据缺失不告警、不记录、不通知（与产品确认）。补充单元测试 `MonitorEventWriterMissingDataTest`（3 项）：:50 仍缺 → 不写事件和发送记录、`last_data_hour` 推进、连续计数中断；:50 前缺 → 等下一轮；有异常中事件时缺数据 → 事件不变。增量脚本在 PostgreSQL 16 上验证：旧记录删除、可重复执行、新库与升级库约束一致、再写 `data_missing` 会被约束拒绝。
