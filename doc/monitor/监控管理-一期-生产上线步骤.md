# 监控管理 · 一期 · 生产上线步骤

2026-10-23 整理，按测试环境当前代码。发布顺序沿用《前后端发版规范》：代码检查 → RDS SQL → 后端 JAR → 后端验证 → 前端 → CloudFront 刷新 → 全链路验收。

### 2.1 现状检查（先看，再执行）

```sql
-- 已有哪些 monitor 表（全新环境为空）
SELECT table_name FROM information_schema.tables WHERE table_name LIKE 'monitor\_%' ORDER BY 1;
-- 指标表是否已改过（有 monitorable = 已执行过 alter_metric_card_monitor；有 alert_min = 还没执行）
SELECT column_name FROM information_schema.columns
 WHERE table_name = 'dashboard_metric_card' AND column_name IN ('monitorable', 'alert_min');
-- 角色是否已带站点
SELECT column_name FROM information_schema.columns WHERE table_name = 'sys_role' AND column_name = 'site_code';
-- 菜单 160–167 必须空着或已经是监控管理（perms 以 monitor: 开头 / route_name = monitor）。被其他菜单占用时先停下来处理
SELECT menu_id, menu_name, route_name, perms FROM sys_menu WHERE menu_id BETWEEN 160 AND 167 ORDER BY 1;
-- 菜单多语言表必须存在（SysMenuMapper 依赖）
SELECT to_regclass('sys_menu_i18n');
```

### 2.2 备份

```bash
TS=$(date +%Y%m%d%H%M)
pg_dump -t dashboard_metric_card -t sys_role -t sys_menu -t sys_menu_i18n -t sys_role_menu -Fc \

# 指标表还有旧告警字段时（2.1 查到 alert_min）：导出旧值，回滚恢复用
```

### 2.3 执行（顺序不能换）

脚本自带事务，不要加 `--single-transaction`；全部可重复执行。

> 已汇总为一个文件 `sql/release_monitor_p1_postgresql.sql`（下面 10 个脚本按顺序原样拼接，开头加了前置检查、末尾加了汇总自检），可直接执行：
> `psql -X -v ON_ERROR_STOP=1 -f release_monitor_p1_postgresql.sql`。下面分步执行与之等价。

```bash
P="psql -X -v ON_ERROR_STOP=1 -f"
$P alter_sys_role_site_postgresql.sql                 # ① sys_role.site_code（新 JAR 启动前必须有，否则登录 / 角色查询报错）
$P alter_metric_card_monitor_postgresql.sql           # ② 指标监控属性 + 删旧告警字段（末尾自检：可监控 20、有刻度 7）
$P monitor_schema_postgresql.sql                      # ③ 7 张 monitor 表 + SITE-IN 站点设置行（已存在的表不动）
$P alter_monitor_engine_postgresql.sql                # ④ 判定引擎列（老表补列；新表无变化）
$P alter_monitor_site_package_network_postgresql.sql  # ⑤ 站点所属包网
$P alter_monitor_event_mute_postgresql.sql            # ⑥ 通知状态 muted + mute_sent_at / mute_hours
$P alter_monitor_event_notify_paused_postgresql.sql   # ⑦ 通知状态 paused（必须在 ⑥ 之后，⑥ 会重建同一个 CHECK）
$P add_monitor_notify_template_postgresql.sql         # ⑧ 通知模板表 + notify_log 模板列 + 菜单「通知模板」
$P add_monitor_menu_postgresql.sql                    # ⑨ 监控管理菜单 160–167
$P add_system_site_menu_postgresql.sql                # ⑩ 菜单「站点管理」（menu_id 取当前最大值 + 1）
```

### 2.4 自检

```sql
-- 8 张：monitor_event / hour_check / lark_chat / notify_log / notify_template / rule / rule_state / site_setting
SELECT table_name FROM information_schema.tables WHERE table_name LIKE 'monitor\_%' ORDER BY 1;
-- 20 / 7
SELECT count(*) FILTER (WHERE monitorable) AS monitorable, count(*) FILTER (WHERE gauge_min IS NOT NULL) AS gauge
  FROM dashboard_metric_card;
-- 通知状态 CHECK 含 muted、paused
SELECT pg_get_constraintdef(oid) FROM pg_constraint WHERE conname = 'ck_monitor_event_notify';
-- 菜单：监控管理 8 行 + 站点管理 2 行 + 通知模板 2 行
SELECT menu_id, menu_name, parent_id, perms FROM sys_menu
 WHERE menu_id BETWEEN 160 AND 167 OR perms LIKE 'system:site:%' OR perms LIKE 'system:notifyTpl:%' ORDER BY menu_id;
```

## 3. 配置同步（`/etc/fivetech.env`，仅 root 可读）

`application.yml` 随 JAR 发布，生产差异只放环境变量。值通过安全渠道获取，不写进 git、聊天、文档。

| 变量 | 生产取值 | 说明 |
|---|---|---|
| `MONITOR_LARK_APP_ID` / `MONITOR_LARK_APP_SECRET` | 生产 Lark 自建应用 | 必配。应用需开通 `im:chat:readonly`、`im:message:send_as_bot` 并启用机器人能力；不配时沿用 `LARK_APP_ID / LARK_APP_SECRET` |
| `MONITOR_ENGINE_ENABLED` | **首次上线 `false`** | 判定 + 发送总开关，见第 6 节再打开 |
| `MONITOR_MAX_ENABLED_RULES` | `40` | 每站启用规则上限 |
| `MONITOR_LARK_CHATS_CACHE_SECONDS` | `30` | 群列表缓存秒数，可不配 |
| `MONITOR_ENGINE_POLL_CRON` / `MONITOR_NOTIFY_CRON` | 不配（默认每 10 分钟 / 每分钟第 30 秒） | |
| `MONITOR_EVENT_PAGE_URL` | 一期不配 | 模板占位符 eventUrl，空则不带链接 |
| `DASHBOARD_SITE` / `DASHBOARD_SITE_NAME` | `SITE-IN` / `uWin` | 默认站点（与测试一致即可，确认） |
| `DASHBOARD_SITE_JITO_CODE` / `_NAME` / `_UDS_SITE` / `_TIMEZONE` | 与 UDS 确认生产值（测试为 `JITO` / `jito` / `SITE-B` / 空） | 第二个站点；`uds-site` 必须是 UDS 生产侧的站点标识，填错会取到别站数据或报错 |
| `DASHBOARD_IP_WHITELIST_ENABLED` / `DASHBOARD_IP_WHITELIST` | 按客户要求；不确定先 `false` | 开启后整个系统只允许名单 IP（含登录） |

配置注意：

- `monitor.engine.baseline-fields`（跌幅基准列名）写在 application.yml 里，UDS 生产列名与测试不同时改 yml 重新打包，不走环境变量。
- `/system/site`、`/system/notify-templates` 不在管理端 IP 白名单的放行路径里，只能从公司内网 IP 访问（设计如此）；`/monitor/**` 已放行。
- Redis 必须可用：Lark token 缓存、判定 / 发送锁、群列表缓存都用它。

改完：

```bash
sudo chmod 600 /etc/fivetech.env
sudo grep -c '^MONITOR_LARK_APP_SECRET=' /etc/fivetech.env    # 只看有没有，不打印值
```

| 数据 | 怎么来 | 生产要做的事 |

| 站点专用通知模板 | 测试环境如有改过且要带到生产，见下方导出 | 可选 |

| 告警规则 / 事件 | **不从测试同步**（测试规则指向测试群和测试负责人） | 运营在生产按需新建；首次建议先建 1～2 条观察 |

测试环境站点专用模板导出（有才需要；在测试库执行，生成的 SQL 在生产执行。content 里的 `{{…}}` 用 `$tpl$` 包起来，psql / DBeaver 不会当成绑定参数）：

```sql
SELECT format(
  'INSERT INTO monitor_notify_template (site_code, notify_type, platform, msg_format, content, enabled, version, remark, create_by, create_time, update_by, update_time) '
  'SELECT %L, %L, ''lark'', ''text'', $tpl$%s$tpl$, %s, 1, %L, ''migrate'', CURRENT_TIMESTAMP, ''migrate'', CURRENT_TIMESTAMP '
  'WHERE NOT EXISTS (SELECT 1 FROM monitor_notify_template WHERE site_code = %L AND notify_type = %L AND platform = ''lark'');',
  site_code, notify_type, content, enabled, remark, site_code, notify_type)
FROM monitor_notify_template WHERE site_code IS NOT NULL ORDER BY site_code, notify_type;
```

全站默认模板如在测试改过，直接在生产「系统管理 › 通知模板」页面改，不用 SQL（保留版本号和修改人）。

## 6. 打开判定引擎（单独一步，不和发版同时做）

前置条件（都满足才打开）：

1. UDS 生产 `dashboard_overview_hour_v2` 水位按小时推进（待确认 #8）；
2. 跌幅类基准列名已与 UDS 确认，并与 `baseline-fields` 一致（待确认 #7）；没有的跌幅类规则会显示「判定失敗」，其他规则不受影响；
3. 生产 Lark 应用在 Lark 后台已开通两个权限，机器人已在告警群里；
4. 至少有一条启用规则选了真实群。

```bash
sudo sed -i 's/^MONITOR_ENGINE_ENABLED=.*/MONITOR_ENGINE_ENABLED=true/' /etc/fivetech.env   # 没有这一行就追加
sudo systemctl restart fivetech
sudo journalctl -u fivetech -f | grep '\[monitor\]'
```

观察 2～3 个整点：每 10 分钟有 `站点 … 数据小时 …：落库=true`；`monitor_hour_check` 每小时 `judged`；严重事件能收到 Lark 卡片 / 消息。用 `doc/monitor/monitor_inspect.sql` 看规则状态和事件。

出问题直接把 `MONITOR_ENGINE_ENABLED` 改回 `false` 重启即可，页面功能不受影响。

## 9. 回滚

| 情况 | 做法 |
|---|---|
| 只是告警有问题 | `MONITOR_ENGINE_ENABLED=false` 重启，不回滚 JAR |
| 后端 JAR 回滚 | **先**执行 `rollback_metric_card_monitor_postgresql.sql`（加回旧告警字段，旧 JAR 启动需要），**再** `sudo yata-deploy rollback` |
| 前端回滚 | 同步上一版 release 目录到 `frontend/dist/`，刷新 CloudFront |

- monitor_* 表、新增列、菜单、sys_role.site_code 对旧 JAR 无影响，保留不删，下次发布不用重建。
- 旧告警字段的值旧代码不使用；确需恢复用 2.2 的 csv 回填（方法同《第一批部署与验证》第 7 节）。
- yata-deploy 健康检查失败会自动回滚 JAR，而旧 JAR 读不到已删的字段也会起不来：出现时立即执行上面的 rollback SQL。
