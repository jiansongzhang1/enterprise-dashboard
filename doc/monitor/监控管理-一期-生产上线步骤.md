# 监控管理 · 一期 · 生产上线步骤

2026-10-29 更新（10-23 初版），按测试环境当前代码。发布顺序沿用《前后端发版规范》：代码检查 → RDS SQL → 后端 JAR → 后端验证 → 前端 → CloudFront 刷新 → 全链路验收。

本次上线 = 监控管理一期全部内容（第一批 CRUD、第二批判定引擎、Lark 群拉取与告警发送、通知模板、站点管理、多站点角色），以及 10-23 之后的：手动触发测试告警、负责人候选按站点过滤、系统管理 · 指标管理（指标口径与取数方式）、回测预览平时水平改由 UDS `metric_distribution_v1` 提供、每次请求 UDS 都带 `X-Uds-Site`。生产不管之前做到哪一步，都按本文从头执行：所有 SQL 都可重复执行。

### 1.5 UDS 前置确认（生产，三项都满足才发后端）

   ```bash
        --key /opt/fivetech/uds-client/client.key -H 'Content-Type: application/json' -H 'X-Uds-Site: SITE-IN' \
        --data-binary @overview_hour_1h.json 'https://<生产 UDS>:8443/v1/query'   # 任一 dashboard_overview_hour_v2 的小时查询
   ```

2. **生产有 `metric_distribution_v1`**，返回 `p5 / p95 / min / max / min_at / max_at / valid_point_count`，且来源是生产数据（联调时是 `ads-test`，生产事实最新只到 09-30）。

### 2.4 自检

```sql
-- 8 张：monitor_event / hour_check / lark_chat / notify_log / notify_template / rule / rule_state / site_setting
SELECT table_name FROM information_schema.tables WHERE table_name LIKE 'monitor\_%' ORDER BY 1;
-- 20 / 7
SELECT count(*) FILTER (WHERE monitorable) AS monitorable, count(*) FILTER (WHERE gauge_min IS NOT NULL) AS gauge
  FROM dashboard_metric_card;
-- 通知状态 CHECK 含 muted、paused
SELECT pg_get_constraintdef(oid) FROM pg_constraint WHERE conname = 'ck_monitor_event_notify';
-- 菜单：监控管理 8 行 + 站点管理 2 行 + 通知模板 2 行 + 手动触发 1 行 + 指标管理 4 行
SELECT menu_id, menu_name, parent_id, perms FROM sys_menu
 WHERE menu_id BETWEEN 160 AND 167 OR perms LIKE 'system:site:%' OR perms LIKE 'system:notifyTpl:%'
    OR perms = 'monitor:rule:test' OR perms LIKE 'system:metric:%' ORDER BY menu_id;
-- 卡片图形 BAR 为 0；指标字典 28 / 28 / 25（net、ngr、pay 由后端组装，没有 UDS 字段）
SELECT count(*) FILTER (WHERE chart_type = 'BAR') AS bar_left, count(*) AS total,
       count(*) FILTER (WHERE remark LIKE '口径：%') AS with_definition,
       count(*) FILTER (WHERE coalesce(uds_hour_field, uds_day_field, uds_amount_field) IS NOT NULL) AS with_uds_field
  FROM dashboard_metric_card;
```

## 3. 配置同步（`/etc/fivetech.env`，仅 root 可读）

`application.yml` 随 JAR 发布，生产差异只放环境变量。值通过安全渠道获取，不写进 git、聊天、文档。

| 变量 | 生产取值 | 说明 |
|---|---|---|
| `MONITOR_LARK_APP_ID` / `MONITOR_LARK_APP_SECRET` | 生产 Lark 自建应用 | 必配。应用需开通 `im:chat:readonly`、`im:message:send_as_bot` 并启用机器人能力；不配时沿用 `LARK_APP_ID / LARK_APP_SECRET` |
| `MONITOR_ENGINE_ENABLED` | **首次上线 `false`** | 判定 + 发送总开关，见第 6 节再打开 |
| `MONITOR_MAX_ENABLED_RULES` | `40` | 每站启用规则上限 |
| `MONITOR_LARK_CHATS_CACHE_SECONDS` | `30` | 群列表缓存秒数，可不配 |
| `MONITOR_ENGINE_POLL_CRON` / `MONITOR_NOTIFY_CRON` | 不配（默认每 10 分钟 / 每分钟第 30 秒） | |
| `MONITOR_EVENT_PAGE_URL` | 一期不配 | 模板占位符 eventUrl，空则不带链接 |
| `MONITOR_TEST_CHAT_ID` | 生产测试群的 chat_id（oc_ 开头） | 管理后台「手動觸發規則（測試）」固定发到这个群；机器人须已在群里。不配时该功能返回「未配置測試群」，不影响其他功能 |
| `DASHBOARD_DEFAULT_UDS_SITE` | `SITE-IN`（与 UDS 确认） | 默认站点在 UDS 的站点标识，每次请求 UDS 都带（第 1.5 节） |
| `UDS_DISTRIBUTION_DATASET` | 不配（默认 `metric_distribution_v1`） | 回测预览平时水平的数据集；置空 = 不接入，平时水平返回 notConfigured |
| `DASHBOARD_SITE` / `DASHBOARD_SITE_NAME` | `SITE-IN` / `uWin` | 默认站点（与测试一致即可，确认） |
| `DASHBOARD_SITE_JITO_CODE` / `_NAME` / `_UDS_SITE` / `_TIMEZONE` | 与 UDS 确认生产值（测试为 `JITO` / `jito` / `JITO` / 空；只在首次启动导入站点表时生效，之后以站点管理为准） | 第二个站点；`uds-site` 必须是 UDS 生产侧的站点标识，填错会取到别站数据或报错；不配时用站点编码。`_TIMEZONE` 是该站点在 UDS 的统计时区：getInfo、运营总览、指标汇总、明细查询、导出都按它（之后在站点管理改）；告警判定与回测仍按 `DASHBOARD_TIMEZONE` |
| `DASHBOARD_IP_WHITELIST_ENABLED` / `DASHBOARD_IP_WHITELIST` | 按客户要求；不确定先 `false` | 开启后整个系统只允许名单 IP（含登录） |

配置注意：

- `monitor.engine.baseline-fields`（跌幅基准列名）写在 application.yml 里，UDS 生产列名与测试不同时改 yml 重新打包，不走环境变量。
- `/system/site`、`/system/notify-templates`、`/system/metrics` 不在管理端 IP 白名单的放行路径里，只能从公司内网 IP 访问（设计如此）；`/monitor/**` 已放行（含 `/monitor/rules/{id}/test-alert`，靠 `monitor:rule:test` 权限控制）。
- 回测预览平时水平的 20 个指标编码映射（dOkR → deposit_success_rate 等）在 application.yml 的 `dashboard.gateway.uds.distribution.metrics`，UDS 生产编码不同时改 yml 重新打包。
- Redis 必须可用：Lark token 缓存、判定 / 发送锁、群列表缓存都用它。

| 菜单授权 | 脚本只授权超级管理员（站点管理、通知模板、指标管理、手动触发测试告警）；监控管理 160–167 不自动授权 | 「角色管理」给 Dashboard 角色勾 160–167；站点角色在角色上选站点（sys_role.site_code）。生产 menu_id 与测试可能不同，按菜单名勾，不要按 id 复制 |

测试环境站点专用模板导出（有才需要；在测试库执行，生成的 SQL 在生产执行。content 里的 `{{…}}` 用 `$tpl$` 包起来，psql / DBeaver 不会当成绑定参数）：

```sql
SELECT format(
  'INSERT INTO monitor_notify_template (site_code, notify_type, platform, msg_format, content, enabled, version, remark, create_by, create_time, update_by, update_time) '
  'SELECT %L, %L, ''lark'', ''text'', $tpl$%s$tpl$, %s, 1, %L, ''migrate'', CURRENT_TIMESTAMP, ''migrate'', CURRENT_TIMESTAMP '
  'WHERE NOT EXISTS (SELECT 1 FROM monitor_notify_template WHERE site_code = %L AND notify_type = %L AND platform = ''lark'');',
  site_code, notify_type, content, enabled, remark, site_code, notify_type)
FROM monitor_notify_template WHERE site_code IS NOT NULL ORDER BY site_code, notify_type;
```

全站默认模板如在测试改过，直接在生产「系统管理 › 通知模板」页面改，不用 SQL（保留版本号和修改人）。

## 9. 回滚

| 情况 | 做法 |
|---|---|
| 只是告警有问题 | `MONITOR_ENGINE_ENABLED=false` 重启，不回滚 JAR |
| UDS 不接受 `X-Uds-Site`（总览、汇总、明细整体报错） | 没有开关可关这个头，直接 `sudo yata-deploy rollback` 回滚 JAR（按下一行先执行 rollback SQL），等 UDS 支持后再发 |
| 后端 JAR 回滚 | **先**执行 `rollback_metric_card_monitor_postgresql.sql`（加回旧告警字段，旧 JAR 启动需要），**再** `sudo yata-deploy rollback` |
| 前端回滚 | 同步上一版 release 目录到 `frontend/dist/`，刷新 CloudFront |

- monitor_* 表、新增列（含 dashboard_metric_card 的 4 个 uds_*_field）、菜单、sys_role.site_code 对旧 JAR 无影响，保留不删，下次发布不用重建。
- ⑪ 卡片图形、⑫ 指标字典不影响旧 JAR，不需要回滚；确需恢复见两个脚本末尾的回滚语句（备份表 `dashboard_metric_card_chart_bak_20261023`、`dashboard_metric_card_bak_20261026`）。
- 旧告警字段的值旧代码不使用；确需恢复用 2.2 的 csv 回填（方法同《第一批部署与验证》第 7 节）。
- yata-deploy 健康检查失败会自动回滚 JAR，而旧 JAR 读不到已删的字段也会起不来：出现时立即执行上面的 rollback SQL。
